# Validation scope

`public-tests.txt`, `public-lint.txt`, and `public-build.json` are generated by `tools/build_release.py` from actual local execution.

## Full suite: HA 2026.10.4

The **125 tests** use the real Home Assistant test runtime. They cover exact-model selection, OAuth state/expiry/reauth using synthetic credentials, readable decoding, duplicate suppression, persistence, setup/unload/removal, synthetic MQTT parsing, mocked cloud HTTP requests, HACS metadata, installed dependency metadata, and browser-facing setup response serialization. They also exercise stage-specific failure messages, real transport error parsing with mocked HTTP responses, safe numeric-code validation, secret-bearing exception redaction, and a post-consent callback-host substitution. External connections are blocked; setup HTTP tests allow loopback only. No test controls a lock.

## Setup and diagnostic smoke test: HA 2026.11.1

`public-smoke-ha-2026.11.1.json` records a real, fresh HA bootstrap with a disposable configuration and synthetic local administrator. The bootstrap loads `http`, `config`, and `webhook`; the latter normally comes from `default_config` and is needed for callback routing. The integration does not currently auto-load it in minimal custom configurations.

The test exercises authenticated POST `/api/config/config_entries/flow`, verifying HTTP 200 with the region form. With `--exercise-failures`, it then starts isolated flows, delivers synthetic codes/state through the actual loopback webhook route, and forces token-exchange and device-discovery errors using mocked cloud methods. It verifies the HTTP abort payload, English message formatting, secret-payload exclusion, and flow/auth cleanup. The reported API/error codes are **deliberately synthetic test values**, not responses from Xiaomi or evidence about a user's failure. No real account is authorized, no cloud endpoint is contacted, and no integration entry is created. The temporary config is removed afterward. Non-loopback socket connections are blocked; HA's network-detection probes may produce blocked-socket warnings.

These are backend HTTP response and message-format checks, not browser pixel/rendering tests or a live authorization success claim.

The available `pytest-homeassistant-custom-component==0.13.375` harness targets HA 2026.10.4 and imports a logger helper removed in 2026.11.1. Therefore the **full 125-test suite is not claimed as passing on 2026.11.1**. The independent smoke test avoids modifying HA or inventing replacement test helpers. `tools/run_tests.py` initializes HA before pytest plugins to preserve HA's HTTP/schema compatibility aliases.

To reproduce the smoke test in a separate local environment:

```sh
uv venv --python 3.14 .venv-smoke
uv pip install --python .venv-smoke/bin/python homeassistant==2026.11.1 paho-mqtt==2.1.0 pytest-socket==0.8.1
.venv-smoke/bin/python tools/smoke_setup.py --scratch /path/to/your/local/scratch --exercise-failures
```

Never point diagnostic tools at a live HA configuration. The smoke tool creates its own disposable subdirectory under the explicitly supplied scratch parent.

## Dependency regression

`public-dependencies.json` records actual uv dry-run resolution checks against both Core versions. The removed 9.1.2 pin conflicts with HA 2026.11.1's exact 9.1.3 requirement; the corrected manifest resolves with both tested Core versions. The dependency tests also check installed package metadata without relying on the HA fixture's mocked requirement installer. Do not override Core-owned package versions on a live instance.

## Evidence boundaries

Synthetic fingerprint and palm-code tests verify decoding, not live biometric recognition. The normal fingerprint event's meaning was separately corroborated through an existing integration. No private device identifiers, household timestamps, credential IDs, raw histories, or biometric payloads are published.

## Isolated live token exchange

The separately approved v0.1.3 candidate used the actual integration's login initialization and retained token client from a temporary loopback server on a Mac. It returned **HTTP 200 / API code 0**, with required token fields present. The preceding same-Mac comparison returned success for upstream-style defaults and API -6 for v0.1.2-style defaults. The candidate changes several conventions together; no single causal field was isolated. See `public-oauth-validation.json` for the allowlisted result, not account data or raw cloud responses.

Tokens were checked in memory and discarded, never copied into HA or used for device discovery/control. No refresh or revocation was performed; local discard does not revoke the vendor-side grant. The temporary listener was stopped and closure verified. This is not a full integration test on the HA VM.

The offline suite additionally verifies pinned transport identity, SDK-derived state, decimal callback identifiers, callback replay rejection and retained-client cleanup on abort/expiry.

## Recorded live delivery and app correlation

A private read-only comparison of user-supplied app logs and HA recorder history matched fingerprint/face/palm labels to standard method codes 2/5/7. Selected palm, inside-operation, locking, visitor and doorbell reports were independently present on this standalone integration's event entities. This establishes actual delivery for those samples, not comprehensive coverage. Some app inside-handle entries lacked fresh standard-cloud counterparts. Property 3/1021 stayed Locked through an observed cycle; app Door closed matches a standard locked action but does not prove physical contact sensing.

New synthetic regressions verify app-description additions without action/state/type changes, exact legacy dedup hashes and suppression of already-seen reports after upgrade. Presentation metadata is excluded from the event identity. Old persisted attributes are not rewritten.

Not yet verified: comprehensive cloud reliability, physical door position, end-to-end latency guarantees, NeonPlan3D rendering or migration of existing automations. No household screenshots, names, timestamps, IDs or histories are published. Existing integrations/automations should remain until the desired behavior is validated.

This is a HACS-compatible custom repository, not a default catalogue entry. The retained upstream license is non-OSI and must not be relabelled to pass a catalogue check.
